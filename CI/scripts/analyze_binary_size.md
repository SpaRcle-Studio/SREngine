# Анализ размера DLL

Запуск из любой рабочей директории:

```bat
C:\Work\SREngine\CI\analyze_binary_size.bat
```

```sh
bash CI/analyze_binary_size.sh
```

Нужен Python 3.9 или новее. Сторонние Python-пакеты не нужны.
Запускатель ищет Python в виртуальном окружении проекта, затем в PATH.
Без аргументов скрипт предлагает выбрать найденную сборку CMake. Поиск идёт
от корня репозитория до трёх уровней вложенности; в найденные сборки и
каталоги зависимостей поиск других сборок не спускается.

Для автоматического запуска:

```text
python CI/scripts/analyze_binary_size.py --input cmake-build-release-visual-studio
python CI/scripts/analyze_binary_size.py --input path/to/Engine.dll --output path/to/report
python CI/scripts/analyze_binary_size.py --input path/to/build --map-dir path/to/maps
```

По умолчанию анализируются DLL внутри Bin, если он существует, иначе внутри
выбранной директории. `--all-dlls` включает поиск во всей сборке, в том числе
среди зависимостей. `--root PATH` меняет корень поиска сборок.
Результат: `BinarySizeReport/report.html` и `report.json` в выбранной директории
(для отдельной DLL — рядом с ней). Повторный запуск перезаписывает отчёты.
Скрипт не запускает сборку, движок, кодогенерацию или внешние инструменты.

## Что показывает отчёт

- Размер DLL на диске и размер PE-образа в памяти.
- Секции: код, данные, константы, ресурсы и служебные таблицы — с их исходными именами.
- Размер каталога экспорта и количество записей символов.
- Семейства шаблонов, уникальные наблюдаемые специализации и число символов,
  в которых они встречаются. В HTML семейство раскрывается до списка специализаций.
- Одинаковые декорированные имена символов в разных DLL.
- При наличии MSVC MAP — 100 крупнейших предполагаемых диапазонов функций
  и исходные обозначения объектов/библиотек из MAP.

На Windows используется системная dbghelp для расшифровки MSVC-имён.
На Linux/macOS секции и экспорты доступны, но декорированные MSVC-имена
не расшифровываются: статистика шаблонов будет неполной или пустой.

## Как интерпретировать шаблоны

Это **не точный счётчик созданных компилятором классов**. По экспортам видны
только сохранившиеся экспортированные символы. Приватные функции, полностью
встроенный код и удалённые специализации в эту статистику не попадут.
Из имён извлекаются шаблонные классы и функции, включая вложенные аргументы.
Число специализаций — количество уникальных шаблонных имён; число символов —
количество уникальных декорированных имён, содержащих это семейство.
Нельзя складывать размеры вложенных семейств: они могут относиться к одному коду.

Много специализаций — повод исследовать семейство. Само по себе это не означает,
что оно занимает много машинного кода. Повторение символа в DLL также не доказывает
побайтовое совпадение реализации или возможность безопасно вынести её в общий модуль.

## MAP и точность размеров

Скрипт ищет `<имя DLL>.map` рядом с DLL, затем рекурсивно в выбранной сборке.
Если найдено несколько кандидатов, автоматический выбор пропускается.
Можно передать отдельный каталог через `--map-dir`.

MAP должен быть создан **той же линковкой**, что и DLL. Скрипт не может
подтвердить их соответствие. Если MAP отсутствует, размеры функций не оцениваются.
Для будущей сборки MAP можно включить опцией MSVC linker `/MAP` для нужной цели;
сам анализатор настройки CMake не меняет.

Размер из MAP — расстояние до следующего известного адреса в том же сегменте.
Он может включать выравнивание, данные и неуказанные символы. Последний адрес
сегмента остаётся без оценки. Алиасы одного адреса имеют одинаковую оценку:
их нельзя складывать. При unity объектный файл представляет группу cpp.
По умолчанию JSON содержит компактную сводку. Для полного списка символов
используй `--full-symbols`: файл может занимать гигабайты. PDB не читается.

## С чего начинать выводы

Обновлённый отчёт сначала показывает вклад библиотек, объектных файлов и
семейств шаблонного кода для каждой DLL. Рейтинг отсортирован по оценке байтов,
а не по количеству имён. Один адрес учитывается один раз; если несколько
владельцев делят адрес, он попадает в отдельную категорию shared address.
Вложенные шаблонные аргументы повторно в байты не суммируются. Семейство-владелец
определяется эвристически по расшифрованному имени; это не точная атрибуция компилятора.

Начни с крупных объектов и библиотек: нужны ли они в runtime, можно ли отключить
неиспользуемую функциональность? Затем смотри семейства шаблонов с большим
суммарным размером: можно ли вынести общую логику из шаблонов или централизовать
инстанцирования? Подтверждай эффект на Release; Debug содержит невстроенные
вызовы и служебный код отладки.

`--top 30` задаёт число строк в рейтингах (по умолчанию 30). HTML всегда
ограничивает подробности; `--full-symbols` расширяет только JSON. Секции показывают
полный размер, рейтинги кода — только оценённые диапазоны MAP. Данные и константы
в эти рейтинги не входят. Промежутки ограничиваются дисковыми секциями PE и
подсекциями MAP, адреса вне секций и абсолютные символы пропускаются.
Сводка в консоли содержит по пять крупнейших объектов и шаблонных семейств.

## Прогресс и производительность

В каталоге отчёта создаётся `analysis.log` (перезаписывается при запуске).
В нём записываются этапы, длительность обработки DLL, ошибки с traceback,
размер JSON, общее время и статистика кэшей. Путь можно изменить:
`--log-file path/to/analysis.log`.

Консоль показывает прогресс MAP по прочитанным байтам, расчёта диапазонов,
сводки кода и обработки имён по количеству записей. В терминале строка
обновляется не чаще четырёх раз в секунду; при перенаправлении вывода
печатаются отдельные строки с интервалом не менее десяти секунд.
Каждая полоса относится к своему этапу, ETA не является прогнозом всего запуска.
Поиск файлов, сортировка и запись отчёта отмечаются в логе как отдельные операции.

Разбор шаблонов для общей статистики выполняется один раз на уникальное имя,
независимо от количества алиасов и DLL. Расшифровка имён и определение семейства
используют ограниченные кэши по 50 000 записей. Буфер dbghelp переиспользуется.
MAP читается потоком; секции и подсекции ищутся двоичным поиском. Это не делает
анализ полностью потоковым: записи символов остаются в памяти для сравнения
между DLL. `--full-symbols` существенно увеличивает время записи и размер JSON.

Размер PDB не относится к размеру DLL. Байты вне секций включают заголовки,
выравнивание, сертификаты и возможные дописанные данные. Существующие DLL/MAP
могут быть устаревшими: анализатор ничего не пересобирает.
