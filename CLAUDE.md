# Правила разработки SREngine

## Общие правила

- Это C++ игровой движок SREngine.
- Перед использованием существующего API сначала найди его реальную реализацию. Не выдумывай классы, методы, функции или типы.
- Используй существующие абстракции SREngine вместо добавления новых без необходимости.
- Следуй существующему стилю кода проекта.
- Не используй STL без необходимости. Если в проекте уже есть собственный контейнер или тип, используй его.
- Не добавляй лишние абстракции, обёртки или уровни косвенности.
- Не переписывай работающий код только ради изменения стиля.
- Не делай рефакторинг кода, который не относится к текущей задаче.
- Не добавляй комментарии, объясняющие очевидный код.
- Не придумывай "улучшения на будущее", если они не нужны для текущей задачи.

## Главное правило: сначала код, потом анализ

При получении задачи на реализацию или исправление ошибки:

1. Найди минимальный набор файлов, непосредственно относящихся к задаче.
2. Изучи только необходимый код.
3. Как только информации достаточно для реализации — сразу начинай изменять код.
4. Не анализируй весь проект перед началом реализации.
5. Не просматривай рекурсивно все зависимости только для того, чтобы "понять архитектуру".
6. Не пытайся полностью понять проект перед первым изменением.
7. Сначала сделай минимальную рабочую реализацию.
8. После первого изменения собери затронутую часть проекта.
9. Используй реальные ошибки компилятора, тестов и runtime для дальнейшего исследования.
10. Исследуй дополнительные файлы только тогда, когда они действительно нужны для реализации или исправления конкретной ошибки.

Нельзя тратить длительное время только на исследование проекта, не внося изменений.

Предпочтительный цикл работы:

найти → изменить → собрать → получить ошибку → исследовать причину → исправить → собрать снова

а не:

исследовать весь проект → исследовать зависимости → строить архитектурную модель → планировать → только потом писать код.

## Минимальность изменений

- Вноси минимальные изменения, необходимые для решения задачи.
- Не меняй публичный API без необходимости.
- Не переименовывай существующие сущности без необходимости.
- Не перемещай файлы без необходимости.
- Не исправляй unrelated code.
- Если существующая архитектура позволяет решить задачу локально — решай её локально.
- Не создавай новую систему, если необходимое поведение можно добавить в существующую.

## Работа с неоднозначностью

Если задача немного неоднозначна, не останавливай реализацию ради бесконечного исследования.

Сделай наиболее очевидное локальное решение, соответствующее существующему коду проекта.

Если для продолжения действительно не хватает критически важной информации — задай один конкретный вопрос.

Не задавай вопросы, ответы на которые можно получить простым поиском по проекту.

## C++ и стиль SREngine

- Используй существующие типы SREngine.
- Предпочитай существующие контейнеры, строки, указатели и аллокаторы SREngine.
- Не заменяй существующий код на STL-вариант без причины.
- Следуй существующим `SR_*` макросам и атрибутам.
- Не вводи `std::function`, `std::bind`, `std::tuple`, ranges и другие STL-механизмы без необходимости.
- Не добавляй дополнительные wrapper-типы, если они не дают реальной пользы.
- Не используй современные возможности C++ только потому, что они существуют.
- Сохраняй существующую модель владения памятью и lifetime объектов.
- Учитывай существующие платформенные реализации SREngine.

## Архитектура

- Не меняй архитектуру проекта без явной необходимости.
- Не предлагай ECS, если существующая система GameObject/Transform решает задачу.
- Не заменяй существующие системы на сторонние библиотеки без явного требования.
- Не создавай новую подсистему, если задача решается существующей.
- Если архитектурное изменение действительно необходимо, сначала объясни конкретную проблему существующей архитектуры и почему локальное решение невозможно.

## Сборка и проверка

После внесения изменений:

1. Собери затронутый target или наиболее близкую доступную цель.
2. Исправь ошибки, вызванные своими изменениями.
3. Если обнаружены старые unrelated ошибки, не пытайся исправлять их без необходимости.
4. Если полноценная сборка невозможна, проверь код настолько локально, насколько возможно.
5. Не утверждай, что код работает, если он не был проверен.

## Git

- Не создавай commit без явной просьбы.
- Не делай reset, rebase, force push или другие потенциально разрушающие Git-операции без явной просьбы.
- Не изменяй чужие незакоммиченные изменения.
- Перед массовым изменением файлов проверь их текущее состояние.

## Формат работы

При выполнении задачи:

- Не пиши длинный план, если задача простая.
- Не описывай каждый просмотренный файл.
- Не сообщай очевидные промежуточные действия.
- Сначала работай с кодом.
- После завершения кратко укажи:
    - какие файлы изменены;
    - что изменено;
    - какие проверки выполнены;
    - остались ли проблемы.

## Кодогенерация

- Все `cpp` файлы автоматически добавляются в сборку после перезагрузки CMake. Не нужно вручную добавлять их в CMakeLists.txt.
- Если в `h` файле есть `SR_ENUM*`, `SR_CLASS` или `SR_STRUCT`, то в соответствующий `cpp` файл необходимо добавить инклюд в самый конец инклюдов `#include <Codegen/FILE_NAME.generated.hpp>`
- Все `cpp` файлы участвующие в кодогенерации должны иметь пару `h` с таким же именем файла. 
- В одном `h` может быть несколько `SR_ENUM*`, `SR_CLASS` или `SR_STRUCT`, кодген файл при этом будет один на все сущности в `h` файле.
- Осуществляется кодогенерация через python скрипт `CI/scripts/codegen.py`. Запрещается вручную его вызывать, как и любые другие скрипты. 

- Кодогенерация поддерживает следующие теги внутри класса через комментарий `///` (ВАЖНО, ИМЕННО ЧЕРЕЗ `///`, а не через `//`): 
  * `@property` - добавляет свойство в класс, которое будет доступно через рефлексию.
  * `@virtualProperty` - добавляет виртуальное свойство в класс, которое не имеет собственного поля, и доступ к нему осуществляется через геттер/сеттер. Например, можно сделать виртуальное свойство `Position`, которое будет возвращать позицию объекта в мировых координатах, а не локальных.
  * `@method` - добавляет метод в класс, который будет доступен через рефлексию.
  * `@condition` - добавляет условие для работы свойства или метода в рантайме. Например, можно указать, что свойство доступно только если выбран соответствующий enum у другого свойства.
  * `@dontSave` - запрещает сериализацию свойства.
  * `@dontLoad` - запрещает десериализацию свойства.
  * `@dontClone` - запрещает клонирование свойства при клонировании объекта.
  * `@readOnly` - делает свойство доступным только для чтения.
  * `@debugOnly` - отображается в редакторе только при включении режима отладки.
  * `@notNull` - запрещает присваивание null значений свойству, автоматически при создании класса инициализируется дефолтным значением, если оно есть.
  * `@dontInitNull` - отключает автоматическое присваивание дефолтного значения свойству с `@notNull` тегом. 
  * `@hidden` - скрывает свойство или метод в редакторе.
  * `@noHeader` - делает свойство (например класс) автоматически развернутым в редакторе, без хедера для раскрытия.
  * `@evaluate` - помечает метод как не влияющий на состояние объекта, предназначен в основном для Flux скриптов.
  * `@editorButton` - добавляет кнопку в редакторе, которая вызывает метод.
  * `@dontPack` - отменяет упаковку возвращаемого значения метода в `SR_UTILS_NS::Reflection::Value`, что позволяет получить значение как есть. Полезно если метод возвращает уже упакованное значение.
  
- Сами классы поддерживают такие теги:
  * `@abstract` - делает класс абстрактным, запрещая его создание.
  * `@noCopyable` - запрещает копирование класса.
  * `@noMovable` - запрещает перемещение класса.
  
## Структура проекта и полезная информация

Проект разделен на несколько модулей:
- Engine - основной игровой движок, работающий со всеми модулями и обеспечивающий их взаимодействие.
- Graphics - модуль, отвечающий за рендеринг и работу с графикой, поддерживает Vulkan и WebGPU. 
- Physics - модуль, отвечающий за физику и взаимодействие объектов в игровом мире.
- Audio - модуль, отвечающий за воспроизведение звука и работу с аудиоэффектами.
- Utils - обширный модуль, содержащий множество систем, начиная от ECS, работы с сетью и сценами/ресурсами, заканчивая платформенными реализациями и стандартными типами данных.
- ImmediateGUI - обертка над Dear ImGui, обеспечивающая интеграцию с движком и его системами, не дает прямого доступа к Dear ImGui, но позволяет использовать его функциональность через собственные абстракции.

Стандартные типы данных в качестве альтернативы STL:
- `SR_UTILS_NS::Optional` - аналог `std::optional`.
- `SR_UTILS_NS::Pair` - аналог `std::pair`.
- `SR_UTILS_NS::Thread` - аналог `std::thread`.
- `SR_UTILS_NS::RawPointerHolder` - аналог `std::unique_ptr`, но предназначен скорее для более удобного владения "сырыми" указателями, чем для управления временем жизни объектов.
- `SR_UTILS_NS::Vector` - аналог `std::vector`.
- `SR_UTILS_NS::Map` - аналог `std::map`.
- `SR_UTILS_NS::Set` - аналог `std::set`.
- `SR_UTILS_NS::String` - аналог `std::string`.
- `SR_UTILS_NS::StringView` - аналог `std::string_view`.
- `SR_HTYPES_NS::FlatHashMap` - аналог `std::unordered_map`.
- `SR_HTYPES_NS::FlatHashSet` - аналог `std::unordered_set`.
- `SR_UTILS_NS::SharedPtr` - аналог `std::shared_ptr`. Но более мощный, больше похож на Intrusive Pointer, с возможностью кастования и без необходимости использования `std::enable_shared_from_this`.
- `SR_HTYPES_NS::Function` - аналог `std::function`, но оптимизированный для избежания лишних аллокаций и с возможностью использования в качестве callback без необходимости создания отдельного объекта.
- `SR_HTYPES_NS::SortedVector` - аналог `std::vector`, но с возможностью хранения элементов в отсортированном виде и поиска по ключу.
- `SR_UTILS_NS::StringAtom` - аналог `std::string`, но с возможностью хранения строк в виде атомов для экономии памяти и ускорения сравнения.

## Прочие нюансы:
- Разрешено использовать из STL только `std::array`, `std::span`, `std::mutex`, `std::shared_mutex`, `std::atomic`, `std::condition_variable` и прочие вещи для синхронизации потоков

- Математика: Вся математика лежит в Utils/Math, включая векторы, матрицы, кватернионы и т.д. Не используй сторонние библиотеки для математики без необходимости.

- По поводу инклудов: Все стандартные типы и STL уже есть в pch, поэтому не нужно их инклудить в каждом файле. Инклудить только то, что реально используется в конкретном файле.

- Вместо int, float, double и подобных используй int32_t, uint32_t, int64_t, uint64_t, float_t, double_t и т.д. Для платформо-зависимых мест есть SR_UTILS_NS::SizeType.
