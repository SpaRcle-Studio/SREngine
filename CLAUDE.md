# Правила разработки SREngine (C++ игровой движок)

## Абсолютные запреты

- **STL-контейнеры** (`std::vector/deque/list/map/unordered_map/set/unordered_set/string/pair/optional/function`, `std::bind`, `std::tuple`, ranges и т.п.) — нигде, включая локальные переменные. Используй аналоги из «Типов» ниже. Встретил STL в правимом коде — замени. Перед сдачей проверь изменённые файлы поиском `std::`. Разрешены только `std::array`, `std::span` и примитивы синхронизации (`mutex`, `shared_mutex`, `atomic`, `condition_variable` и т.п.).
- **Сравнение float/double через `==`** — только `SR_EQUALS`.
- **Документация** — не создавать без разрешения ни в `/Documentation` (публикуется на сайт), ни где-либо ещё.
- **Сборка и запуск** — не запускать `cmake` (включая реконфигурацию: она запускает `CI/scripts/codegen.py`), `ninja`, `msbuild`, `make`, `cl`, `clang`, `vcvars*.bat`, любые скрипты, бинарники и тесты — даже в фоне «для проверки». Собирает пользователь. Если сборку явно попросили — только `/build` (`.claude/scripts/build.py`: CMake с кодогеном + сборка движка), не компилировать отдельные файлы и не вызывать `cmake`/`ninja` напрямую. Запуск движка/тестов по явной просьбе — только `/run` (`.claude/scripts/run.py`).
- **Правка исходников через shell** (python/sed/awk/echo/heredoc) — ломает экранирование строк (`C2001`). Только Edit/Write; shell — для чтения и поиска. После правки перечитай участок и строковые литералы.
- **Git** — без явной просьбы: никаких commit, reset, rebase, force push; не трогать чужие незакоммиченные изменения.

## Подход к работе

- Цикл: найти минимум нужных файлов → сразу изменить → проверить локально → отдать пользователю → по его ошибкам исследовать и исправить. Не изучай весь проект и зависимости перед первым изменением.
- Не выдумывай API — сначала найди реальную реализацию.
- Минимальные изменения: без рефакторинга и правок unrelated-кода, без смены публичного API, переименований и переноса файлов без необходимости, без «улучшений на будущее», лишних абстракций/обёрток и очевидных комментариев.
- Решай локально в существующих системах (GameObject/Transform, а не новый ECS; не заменяй системы сторонними библиотеками). Архитектурное изменение — только с объяснением, почему локально нельзя.
- При неоднозначности делай самое очевидное решение в духе проекта; вопрос — один и только если ответа нет в коде.
- После изменений: сверь сигнатуры/типы поиском; проверь инклюды `Codegen/*.generated.hpp`; сообщи, что код не собирался и нужно пересобрать (и перезагрузить CMake, если есть новые `cpp`). Не утверждай, что компилируется/работает, без подтверждения. Исправляй только ошибки сборки от своих изменений.
- Итог кратко: какие файлы, что изменено, какие проверки, остались ли проблемы.
- Лог последнего запуска: `%LOCALAPPDATA%\SpaRcle-Studio\SREngine\Logs\srengine.log` (не в `Bin` сборки); разбор — `/log` (агент `log-analyst`).

## Сабагенты и skills

- Делегируй только независимые объёмные части; правку в паре файлов или поиск с известной целью делай сам.
- Массовые механические правки (замена типов, каскад сигнатур) — `refactor-worker` (Sonnet), не `fork`: fork идёт на родительской модели с полным контекстом. Fork — только если подзадаче нужна вся беседа.
- Поиск по многим файлам — `Explore`; проверка diff на правила CLAUDE.md — `/precheck` (агент `rules-reviewer`).
- Задание сабагенту самодостаточно: цель, список файлов, изменённые сигнатуры, известные ошибки и что уже исключено. Параллельным агентам — непересекающиеся файлы.
- Сабагенты не собирают; результат проверяет основной агент (поиск `std::`, сигнатуры) и сообщает пользователю, что нужна пересборка.
- Новые файлы — `/new-file`. Заметки систем из списка ниже подгружаются skills `*-notes` автоматически по путям, но перед правкой всё равно их прочитай.
- Hooks в `.claude/settings.json`: shell-правки исходников блокируются; сборка требует подтверждения пользователя (`SRENGINE_ALLOW_BUILD=1` в окружении снимает это на сессию); после Edit/Write `check_source.py` сообщает о нарушениях — исправь или объясни исключение в итоге.

## Стиль C++

- `cpp` — только в `src`, `h` — только в `inc`.
- Guard только `#ifndef SR_ENGINE_<МОДУЛЬ>_<ФАЙЛ>_H`, без `#pragma once`.
- Новые файлы начинаются с шапки (в существующих не менять):
  ```cpp
  //
  // Created by <author> on DD.MM.YYYY.
  //
  ```
- Без анонимных namespace (хелперы — в отдельные файлы с именованным namespace) и без `using` (кроме шаблонного кода и `Super = ...`).
- Не сжимать тела/условия/циклы в одну строку. Пустая строка между методами в `cpp` и между этапами логики; в `h` — смысловые секции.
- Указатели `pName`, поля-указатели `m_pName`. Вывод типов — `auto&&` (а не `auto*`/`auto&`), сохраняя const.
- Осмысленные имена без сокращений (кроме `i, j, x, y, z` и т.п.).
- Типы `int32_t`, `uint32_t`, `int64_t`, `float_t`, `double_t`…; платформо-зависимое — `SR_UTILS_NS::SizeType`.
- Логи (`SR_ERROR/WARN/LOG/INFO`…) начинаются с источника: `ClassName::Method() : ...`.
- Инклюды: группы по модулям через пустую строку; сначала текущий модуль, затем остальные в порядке Engine → Graphics → Physics → Audio → Utils → Codegen → прочие. STL уже в pch — не инклюдить.
- Следуй `SR_*` макросам, модели владения/lifetime и платформенным реализациям. Не используй новые фичи C++ ради самих фич.
- Без устранимых runtime-аллокаций: кешируй, не пересоздавай строки в покадровом коде. Tracy-зоны в значимых операциях (компиляция, перезагрузка, регистрация API, выполнение скриптов); `SR_TRACY_ZONE` и `SR_TRACY_ZONE_N` в одной области конфликтуют — `_N` только во вложенный блок.
- Большие файлы дроби по самостоятельным обязанностям (компоненты/классы/алгоритмы), а не раскладывая методы одного класса по разным `cpp`. Старое разбиение не трогать.
- Необязательные библиотеки: полностью отключаются опцией CMake (без сборки, линковки, заголовков); `cpp` не исключать из CMake — закрывать SDK-код макросом внутри; основные системы и их API создаются и без библиотеки. Заголовки/типы сторонних библиотек не протекают в публичный API.

## Кодогенерация

- Новые `cpp` подхватываются после перезагрузки CMake, в CMakeLists не добавлять.
- `h` с `SR_ENUM*`/`SR_CLASS`/`SR_STRUCT` → в парный `cpp` (то же имя) последним инклюдом `#include <Codegen/FILE_NAME.generated.hpp>` (один на весь `h`).
- Теги рефлексии пишутся через `///`. Перед использованием тегов (`@property`, `@method`, `@dontSave` и др.) или созданием нового хедера модуля прочитай [.claude/docs/Codegen.md](.claude/docs/Codegen.md).

## Структура и типы

Модули: Engine (связывает всё), Graphics (Vulkan, WebGPU), Physics, Audio, Utils (ECS, сеть, сцены/ресурсы, платформа, типы, математика в `Utils/Math`), ImmediateGUI (обёртка над Dear ImGui без прямого доступа к нему).

Типы вместо STL: `SR_UTILS_NS::` `Vector`, `SortedVector` (сортированный, поиск по ключу), `Map`, `Set`, `String`, `StringView`, `StringAtom` (атомизированная строка, быстрое сравнение), `Optional`, `Pair`, `Thread`, `SharedPtr` (intrusive-подобный, с кастами, без `enable_shared_from_this`), `RawPointerHolder` (владение сырым указателем, ~`unique_ptr`); `SR_HTYPES_NS::` `FlatHashMap`, `FlatHashSet`, `Function` (без лишних аллокаций).

`SceneObject::SetEnabled` только помечает объект грязным; активность применяется в `CheckActivity`, `OnEnable` приходит не сразу.

- террейн и трава — [.claude/docs/Terrain.md](.claude/docs/Terrain.md);
- рендер, пайплайн, G-buffer, пост-эффекты — [.claude/docs/Render.md](.claude/docs/Render.md);
- физика — [.claude/docs/Physics.md](.claude/docs/Physics.md);
- игровые проекты (`.srproject`, сцены sra, скрипты AngelScript, граница движок/игра) — [.claude/docs/GameProjects.md](.claude/docs/GameProjects.md).
